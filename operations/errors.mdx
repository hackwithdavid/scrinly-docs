title: "Errors and retries"
description: "Handle transport, capture, component, and asynchronous failures."
---

JSON errors include `success:false`, a safe `error` message, and a stable `type`. Some products add a more specific `code`, `retryable`, `fields`, or settled `credits`.

| Status | Meaning |
| --- | --- |
| `400` | Invalid field, unsupported combination, or malformed source |
| `401` | Missing, invalid, or revoked Scrinly key |
| `402` | Credit allowance exhausted |
| `404` | Unknown or cross-account resource |
| `409` | Conflicting monitor run or state transition |
| `413` | Request or source exceeds a documented limit |
| `422` | Browser could not produce a complete finite capture |
| `429` | Host or provider rate limit |
| `500–503` | Temporary platform, provider, or configuration failure |

## Partial screenshot results

Add-ons settle independently. A successful screenshot with failed regions returns HTTP `200`, `regions:null`, `regionError`, and a two-credit refund. A successful screenshot and regions with failed AI generation returns `status:"partial"`, `styleGuide:null`, a typed `styleGuideError`, and only the AI refund.

Treat partial responses as usable evidence. Persist the complete screenshot and inspect the typed component error before deciding whether to retry. A customer retry can use `cache:true` to avoid another browser capture when the cached entry contains all required inputs.

## Retry guidance

- Retry `429` after `Retry-After`, with jitter.
- Retry errors only when `retryable:true` or the transport failed before a response.
- Do not retry validation, ownership, hash-mismatch, or unbounded-page errors unchanged.
- Make async settlement idempotent on your side by job ID or webhook event identity.
- Polling `GET /status/{jobId}` does not charge credits.

Scrinly does not expose customer retry or recovery routes. Submit a new screenshot or diff request when a retry is appropriate.
